# Activity-Relay v3.1.0

Status: stable release draft.

- Application version: `3.1.0`
- Debian package version: `3.1.0-1`
- Accepted release-candidate baseline: `3.1.0-rc4`

## Stable scope

Activity-Relay 3.1 promotes the accepted 3.1.0-rc4 behavior to stable without
runtime changes. The release extends the optional Activity-Relay Directory
integration, improves operator-facing profile/configuration handling, and keeps
relay delivery, following, actor identity, Redis state, and existing queue/data
compatibility intact.

Directory participation remains opt-in. A relay that does not configure a
Directory continues to operate without Directory traffic.

## Activity-Relay Directory interoperability

The 3.1 line adds negotiated Directory Protocol v2 profile synchronization and
Protocol v3 participating-site telemetry while retaining Protocol v1
compatibility. Protocol v2 registration carries the complete normalized
descriptive profile; v2 heartbeat and unregister remain identity-only. Protocol
v3 may additionally report bounded `participating_instance_count` telemetry
derived from the relay's own connected-instance status.

The client selects the highest lifecycle protocol explicitly advertised by the
Directory. Status transport or validation failure is not treated as downgrade
authority. Persisted scheduler state records the protocol version that last
carried the profile digest so a later v2/v3 negotiation change triggers one
profile reconciliation rather than repeated registration.

## Startup and manual lifecycle operation

Each enabled Directory receives one immediate reconciliation when the API/server
process starts. A known relay with an unchanged profile sends a heartbeat; a new
or profile-changed relay registers. Existing persisted retry, authentication,
suspension, enrollment, rate-limit, and malformed-response deadlines remain
authoritative and are not bypassed by the startup pulse.

Manual `directory register`, `directory heartbeat`, and `directory sync`
commands use the same scheduler lease when file-backed scheduling is enabled. A
successful manual operation advances persisted scheduler state so the background
scheduler does not immediately duplicate it. Register/sync also persist the
normalized profile digest and negotiated profile protocol.

Production RC4 validation confirmed that a normal package restart generated a
fresh Directory heartbeat and restored the relay's current-liveness/Tier-1
projection without a configuration edit.

## Profile and operator changes

`DIRECTORY_PROFILE` supports the reviewed descriptive relay profile used by
Directory Protocol v2/v3. `participation_mode` is restricted to `open`,
`restricted`, `closed`, or empty; invalid optional profile metadata is omitted
with diagnostics rather than preventing normal relay startup.

The local static relay page keeps profile/contact/focus presentation separate,
and `participation_url` remains synchronized to Directories without being
rendered locally. The optional `SUPPORT` block remains presentation-only.

Configuration can be checked before restart with `-t` / `--test-config`, with
optional strict handling for profile diagnostics.

## Directory client hardening

The outbound Directory path uses bounded transport, response, redirect,
terminal-output, and retry behavior. Malformed or malicious Directory responses
remain isolated optional-integration failures and do not alter relay delivery,
following, or ActivityPub service availability.

## Packaging and documentation

The project README is a concise project/install/operator entry point. Detailed
installation, CLI/administration, and contributor/test procedures live in
`docs/INSTALLATION.md`, `docs/ADMINISTRATION.md`, and `docs/DEVELOPMENT.md`.

The canonical Forgejo artifact workflow wraps `public/` and `evidence/` in a
deterministic tar carrier before Actions artifact upload. Canonical public asset
checksums remain authoritative while the carrier preserves expected Unix modes
and deterministic release timestamps across the outer artifact transport.

Native deployments use:

```text
activity-relay_3.1.0-1_amd64.deb
```

Container deployments use the stable `3.1.0` image/tag after registry
publication. Release acceptance is based on the exact canonical artifact set
built from the stable-preparation commit; do not rebuild accepted package or OCI
bytes after tagging.

## Compatibility and upgrade

The stable promotion does not rotate or replace the relay actor, `#main-key`,
public endpoints, Redis instance, subscriptions, publishers, receiver-health
history, or operator-owned website content. Existing task formats remain
readable. Back up the actor key, Redis persistence, configuration, and
operator-owned web content before upgrading according to the normal deployment
procedure.

## Release acceptance

The accepted RC4 line passed source/CI validation, cross-project Protocol v3
interoperability, production startup-heartbeat recovery, and scheduler-state
reconciliation. Stable `3.1.0` is a new source/version preparation and therefore
receives its own canonical build and artifact-transport validation; RC4 artifacts
are not relabeled as stable files.

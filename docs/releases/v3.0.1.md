# Activity-Relay v3.0.1

- Application version: `3.0.1`
- Debian package version: `3.0.1-1`
- Release type: patch reliability release
- Stable outbound-signature default: `dual`

## Release scope

Activity-Relay 3.0.1 is a focused reliability release for follower-style
registration and relay fan-out. It follows diagnosis of an incomplete persisted
follower record that could reach delivery planning with an empty inbox and
prevent otherwise healthy fan-out from being queued.

The release hardens that path at each boundary:

- follower registration validates the domain, actor ID, originating Follow
  activity, and HTTP(S) inbox before persistence;
- mutual-follow status changes may update only an existing complete follower
  record and cannot recreate a deleted follower as a side effect;
- incomplete persisted follower hashes are excluded from the in-memory
  receiving set;
- malformed or unplannable delivery destinations are skipped independently so
  healthy receivers continue to receive relay fan-out; and
- queue reservations and stored remaining-delivery counts reflect only the
  delivery tasks that were actually planned.

Manual follower approval now also commits valid follower state before sending
the remote `Accept`, so a failed state transition cannot acknowledge a follower
that the relay was unable to retain.

## Compatibility and upgrade

3.0.1 does not change the relay actor identity, `#main-key`, ActivityPub
endpoints, configuration schema, Redis instance, task format, or normal
subscription and publisher records. Existing one-way followers with
`mutually_follow = 0` remain valid.

No operator migration is required. Incomplete follower hashes are ignored when
state is loaded; if a mutual-follow status update encounters an incomplete hash,
that invalid hash is removed instead of being extended into a partial record.

Back up the actor key, Redis persistence, configuration, and operator-owned web
content before upgrading according to the normal deployment procedure.

Native deployments use:

```text
activity-relay_3.0.1-1_amd64.deb
```

Container deployments use the stable `3.0.1` image/tag after registry
publication. Release acceptance is based on the canonical multi-architecture OCI
archive built by Forgejo; do not rebuild a second release image from the tag.

## Build and release validation

Forgejo container validation now installs Debian Trixie's split `docker-cli`
and `docker-buildx` packages explicitly. The canonical release-artifact workflow
uses the client-only Docker package because its engine is provided through the
isolated TCP `DOCKER_HOST`; its dedicated Buildx setup step remains authoritative
for the multi-architecture OCI build.

These changes affect release validation infrastructure only and do not change
the runtime container image.

## Pre-publication acceptance

Before publication, build the canonical artifact set from the exact reviewed
3.0.1 release-preparation commit. Verify its checksums and metadata, deploy the
accepted candidate artifacts to the production validation host, and exercise:

- `relay --version`;
- `/actor`, `/nodeinfo/2.1`, and `/status.json`;
- normal worker delivery and retry handling; and
- a real accepted publisher activity reaching a healthy receiving server.

Only after those checks pass should the exact reviewed commit be tagged and the
already accepted bytes be published.

## Release artifacts and authority

Forgejo remains the source and release authority. The manual canonical release
workflow requires the exact reviewed commit, exact `3.0.1` version, and explicit
build confirmation. It emits one checksummed release bundle containing:

- the Ubuntu `amd64` Debian package;
- CycloneDX SBOM;
- `linux/amd64` + `linux/arm64` OCI archive;
- `BUILD-METADATA.txt`;
- `RELEASE-NOTES.md`; and
- `SHA256SUMS`.

The accepted canonical bytes are the release bytes. Tagging, Forgejo release
publication, registry publication, downstream GitHub mirroring, and deployment
remain separate operator-controlled gates and must not rebuild those bytes.

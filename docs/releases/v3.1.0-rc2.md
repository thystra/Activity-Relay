# Activity-Relay v3.1.0-rc2

- Application version: `3.1.0-rc2`
- Debian package version: `3.1.0~rc2-1`
- Stable baseline: `v3.0.1`
- Paired Directory candidate: Activity-Relay Directory `1.3.0-rc2`

> [!IMPORTANT]
> RC2 keeps the accepted Directory Protocol-v2 wire contract unchanged. Its
> production changes are limited to the optional generated landing-site
> presentation and provider-neutral support metadata consumed by that builder.

## RC1 findings addressed

The RC1 live integration proved that Activity-Relay negotiates ARD schema 4,
selects lifecycle Protocol v2, registers its complete descriptive profile, and
has that profile reflected by ARD. RC2 adds the corresponding local presentation
to the bundled relay landing site:

- the same file-backed `DIRECTORY_PROFILE` is rendered near the top of the home
  page when `activity-relay-rebuild-site` reads the relay config;
- `participation_mode` is displayed as **Registration status** and
  `participation_url` as **About this relay**;
- registration/contact/notes information appears before **Relay focus**;
- relay type and topics are grouped under **Relay focus**;
- languages, countries, and regions are shown only when at least one is
  declared; empty lists therefore mean no focus is asserted and need no
  wildcard value; and
- an optional top-level `SUPPORT` sequence renders a collapsed **Support this
  relay** block.

`SUPPORT` accepts at most eight entries. Each requires `title` and exactly one
absolute HTTPS `url` or escaped plain-text `value`. It is ignored by the Go
relay runtime and is never sent to a Directory or ActivityPub peer. The static
site builder accepts no support HTML, Markdown, scripts, embeds, or tracking
pixels.

## Rebuild behavior

The bundled site is static. After changing `DIRECTORY_PROFILE` or `SUPPORT`,
re-run:

```sh
sudo activity-relay-rebuild-site
```

A relay service restart is not required solely to regenerate the static site.
Normal runtime configuration changes may still require the usual relay restart
for their runtime effects.

## Compatibility

Directory Protocol v2 registration, status negotiation, profile digest
reconciliation, heartbeat/unregister behavior, Protocol-v1 fallback, actor/key
identity, follower state, delivery/fan-out, Redis keys, and queue formats are
unchanged from RC1.

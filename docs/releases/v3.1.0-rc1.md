## Summary

Activity-Relay 3.1 adds negotiated Activity-Relay Directory Protocol v2 profile
synchronization while preserving Protocol v1 interoperability. A configured
Directory is queried through `/v1/status`; schema 4 explicitly advertises the
supported lifecycle protocol versions. Activity-Relay selects v2 only when
version 2 is advertised and does not treat malformed status or transport failure
as a downgrade signal.

Protocol-v2 registration sends the canonical relay actor, public base URL, and
a complete twelve-field normalized descriptive profile. Heartbeat and unregister
remain identity-only. Existing v1 client methods remain available for
compatibility and tests; production commands and the scheduler use negotiated
operations.

## Directory profile configuration

File-backed configuration accepts:

```yaml
DIRECTORY_PROFILE:
  participation_mode: open
  availability: public
  relay_type: general
  languages: [en]
  countries: [US]
  regions: []
  topics: [general]
  contact_fediverse: "@relay@example.social"
  contact_email: relay@example.org
  contact_url: https://relay.example.org/contact
  participation_url: https://relay.example.org/join
  notes: "AR 3.1 / ARD 1.3 RC1 live integration test"
```

Normalization trims scalar/list values, deduplicates and sorts list fields,
validates bounded HTTPS/contact values, and hashes the deterministic compact
profile representation for scheduler reconciliation. Empty strings and arrays
are transmitted explicitly by v2 registration so ARD can clear the relay-owned
assertion for those fields.

Environment-only manual commands may supply `DIRECTORY_PROFILE` as the reviewed
YAML mapping form.

## Scheduler and explicit sync

The Directory scheduler stores only a profile digest and the protocol version
used for the last successful profile reconciliation; profile content is not
stored in Redis. When the configured profile changes, the scheduler performs an
immediate negotiated registration rather than waiting for the next heartbeat.
If v2 becomes newly available after prior v1 operation, one v2 registration
reconciles the profile.

`relay directory sync` is an explicit negotiated registration/profile
reconciliation operation. It no longer means heartbeat-first lifecycle repair.

## Compatibility and non-interference

The RC does not rotate the relay actor key, change the actor ID, alter follower
or delivery semantics, migrate Redis state, change queue task formats, or enable
Directory traffic merely because v2 support exists.

Activity-Relay retains Protocol v1 compatibility for Directories that advertise
only v1 through a valid legacy status response. A malformed status response or
failed status request is an error rather than permission to silently downgrade.

Before creating RC artifacts, the normal Forgejo source, Redis-backed, race,
package, Caddy, and container validation workflows must be green on the exact
RC-preparation commit. The shared signed v2 fixture generated by the client must
match the fixture consumed by the paired ARD source.

## Paired ARD 1.3 live acceptance

Deploy the accepted ARD 1.3 RC1 artifacts first, then deploy these accepted AR
3.1 RC1 artifacts to a controlled relay. Required evidence:

1. `relay directory status` observes ARD status schema 4 and lifecycle versions
   `[1,2]`;
2. first negotiated registration uses `/v2/relays/register`;
3. the configured profile appears in ARD's effective public profile;
4. changing `DIRECTORY_PROFILE` and running `relay directory sync` updates ARD;
5. empty profile values clear only relay-owned assertions and expose lower ARD
   CSV assertions where configured;
6. normal negotiated heartbeat does not rewrite the profile;
7. restart/reconciliation does not create repeated unnecessary registrations
   when the profile digest is unchanged;
8. an ARD instance advertising only Protocol v1 causes valid v1 fallback; and
9. malformed/failed capability discovery remains fail-closed rather than
   silently downgrading.

Any production-code change discovered during this paired exercise requires a
new release candidate.

## RC1 validation and promotion gates

Before creating tag `v3.1.0-rc1`:

1. run the complete Forgejo validation matrix on the exact RC-preparation
   commit;
2. run the canonical release workflow with the exact full commit, version
   `3.1.0-rc1`, and confirmation `BUILD 3.1.0-rc1`;
3. inspect and retain the exact Debian, CycloneDX SBOM, multi-architecture OCI,
   checksum, Lintian, build-metadata, and OCI-index evidence; and
4. prove the accepted artifact bytes can be published without rebuilding them.

After the artifact set is accepted, create/publish the RC tag and exact retained
bytes, deploy the paired RCs, and perform the live gate above. Stable promotion
uses a separate source/release preparation after live acceptance; accepted RC
artifacts are not relabeled as stable.
